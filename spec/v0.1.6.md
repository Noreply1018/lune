# v0.1.6 Draft: Streaming Completion Accounting, Activity Flow, and Lightweight VPS Runtime

Status: draft

## Goal

Make streaming proxy failures visible and trustworthy in Activity, especially when an upstream stream closes before the protocol-level completion event.

Upgrade the Activity flow visualization from `Pool -> Model` to `Pool -> Account -> Model` so routing behavior is easier to inspect.

## Current Problem

Lune currently forwards streaming responses directly to the client and treats the stream as finished when the response body reader ends.

This misses several failure modes:

- The upstream stream closes before `[DONE]` or `response.completed`.
- The upstream stream emits a semantic failure event such as `response.failed`.
- The upstream read fails after response headers have already been written.
- A large SSE line exceeds the current scanner limit.
- Writing to the downstream client fails mid-stream.
- The gateway request timeout terminates a long stream.

In these cases, client SDKs can report errors such as:

`stream disconnected before completion: stream closed before response.completed`

Another observed example is an upstream capacity failure surfaced by the client:

`Selected model is at capacity. Please try a different model`

Activity may still show the request as successful because the stream forwarding path does not return read/write/completion errors to the gateway handler.

## Draft Direction

- [x] Replace the stream forwarding return value with structured stream metadata: usage, completion state, protocol marker, and terminal error.
- [x] Detect OpenAI Chat Completions completion via `[DONE]`.
- [x] Detect OpenAI Responses completion via `response.completed`.
- [x] Treat `response.failed`, `response.incomplete`, scanner/read errors, write errors, and EOF before completion as failed stream outcomes.
- [x] Extract upstream semantic error messages from stream events, including model capacity errors.
- [x] Record failed stream outcomes in Activity even when the HTTP status already sent to the client was `200`.
- [x] Preserve partial usage when it can be parsed before failure.
- [x] Avoid retrying after any stream bytes have been written to the client.
- [~] Revisit `bufio.Scanner` for SSE forwarding; current implementation records scanner failures instead of silently treating them as success, but a reader-based forwarder remains a follow-up.

## Activity Semantics

For a stream that received a successful upstream HTTP status but did not reach a completion marker:

- `status_code` should remain the upstream HTTP status, usually `200`.
- `success` should be `false`.
- `error_message` should explain the stream terminal condition, for example `stream closed before response.completed`.
- For upstream semantic failures, `error_message` should preserve the upstream message, for example `Selected model is at capacity. Please try a different model`.
- `latency_ms`, `pool_id`, `account_id`, `source_kind`, `attempt_count`, and any parsed usage should still be recorded.

## Capacity Failure Semantics

The message `Selected model is at capacity. Please try a different model` is not generated by Lune. It is an upstream model/account capacity failure surfaced through the client protocol.

Lune's responsibility is to avoid misclassifying that request as successful:

- If the capacity failure arrives before response headers or stream bytes are sent, normal retry may still be possible.
- If the capacity failure arrives after stream output has started, Lune should not retry because the downstream response is already committed.
- In both cases, Activity should record the routed pool/account/model and the upstream capacity message.
- A stream-level capacity failure should not clear an existing account error state or mark the account healthy just because the HTTP status was `200`.

## Observed CPA Stream Failover Gap

An observed production failure pattern on 2026-05-06 showed repeated CPA stream failures for `POST /api/provider/codex/v1/responses` routed to the first Pool account.

The CPA error log files were written under:

`/app/data/cpa-auth/logs/error-api-provider-codex-v1-responses-*.log`

The host-mounted path in that deployment was:

`/mnt/c/Users/lh/lune-data/cpa-auth/logs/`

The CPA response body contained the real upstream failure:

`Post "https://chatgpt.com/backend-api/codex/responses": EOF`

However, Activity only recorded repeated rows like:

- `source_kind=cpa`
- `model_requested=gpt-5.5`
- `status_code=500`
- `error_message=upstream error`
- `stream=true`
- `attempt_count=1`

The failures stayed on `account_id=1` instead of moving to `account_id=2` because the current streaming retry branch returns early for retryable HTTP statuses. That early return happens before the failed account is excluded from the retry set or marked unhealthy/degraded.

The intended v0.1.6 behavior should be:

- [x] When a streaming upstream returns a retryable status such as `500` before Lune can safely retry, Lune must still record account health impact.
- [x] The failed account should be marked `error` or `degraded`, or otherwise made temporarily avoidable by subsequent route resolution.
- [x] Subsequent independent requests should be able to route to the next healthy Pool member instead of repeatedly selecting the first account.
- [x] Lune must still avoid retrying a stream after response bytes have been committed to the downstream client.
- [x] The implementation should distinguish "cannot retry this already-committed stream" from "do not update routing health"; these are separate concerns.

## Upstream Error Detail Preservation

Activity should preserve useful upstream error details when Lune receives a structured upstream error body.

The current generic `upstream error` message is not enough for diagnosis. In the observed CPA EOF case, the actionable message was available in the CPA response body, but not in `request_logs.error_message`.

For v0.1.6:

- [x] If a retryable upstream HTTP response contains a JSON error body, extract the best available message into `request_logs.error_message`.
- [x] For CPA errors, preserve messages such as `Post "https://chatgpt.com/backend-api/codex/responses": EOF`.
- [x] Keep the message bounded so a large response body cannot bloat SQLite or the Activity API.
- [x] Do not expose credentials or full request bodies in Activity.
- [x] Prefer a concise normalized message over a generic `upstream error` when the upstream body provides one.
- [x] If no safe message can be extracted, keep the generic fallback.

## Test Cases

- [x] Chat Completions stream ends without `[DONE]`; Activity records failure.
- [x] Responses stream ends without `response.completed`; Activity records failure.
- [x] Responses stream emits `response.failed`; Activity records failure and preserves the upstream status.
- [x] Responses stream emits `response.failed` with `Selected model is at capacity. Please try a different model`; Activity records failure with that message.
- [x] Responses stream emits `[DONE]` without `response.completed`; Activity still records failure.
- [x] CPA stream returns HTTP 500 with a JSON error body before completion; Activity records the extracted upstream message instead of only `upstream error`.
- [x] CPA stream returns HTTP 500 for the first Pool account; Lune records health impact so subsequent independent requests can avoid that account and select the next healthy Pool member.
- [x] Streaming retryable status on a single/final attempt still records account health impact.
- [x] SSE line exceeds the previous 1MB scanner limit; Activity records a stream read error instead of success.
- [x] Downstream write fails after headers are sent; Activity records failure.
- [x] Long stream exceeds gateway timeout; Activity records timeout-related failure.

## Open Questions

- Should stream timeout use a separate setting from non-stream request timeout?
- Should EOF before completion mark account health as error, degraded, or only request-level failure?
- Should the UI show a distinct `stream_incomplete` badge instead of only a failed request row?
- Should stream retryable-status health impact be a fixed `error`, a softer `degraded`, or a time-limited circuit-breaker state?
- What exact max length should `request_logs.error_message` use for extracted upstream messages?

## Activity Flow Upgrade

The current Activity Sankey diagram aggregates recent request logs into two columns:

- Pool
- Model

The next version should show three columns:

- Pool
- Account
- Model

## Flow Data Semantics

The existing request log API already carries the fields needed for a first implementation:

- `pool_id`
- `account_id`
- `account_label`
- `model_requested`
- `model_actual`

The visualization should build two link sets:

- `pool -> account`
- `account -> model`

The diagram should describe the final recorded route for each request log row. It does not currently describe every retry attempt, because request logs store the final routed account and aggregate attempt count, not per-attempt account history.

## Flow UI Requirements

- Rename the section to `Pool -> Account -> Model`.
- Update the section description and tooltip text to match the three-step path.
- Keep the same rolling 24h source window used by the existing flow view.
- Add a middle account column with labels based on `account_label`, falling back to `#account_id`.
- Handle route-rejected rows where no account was selected; either group them under a clear `Unrouted` node or exclude them from the flow with copy that explains the exclusion.
- Preserve readable labels on narrow screens by allowing horizontal scroll and increasing the SVG viewBox width from the current two-column layout.

## Flow Open Questions

- Should failed routed requests be included in the flow by default, or should the flow show only successful requests?
- Should retries eventually be represented as per-attempt paths? That would require richer request log data than the current final-account record.
- Should `pool_label` be added to the request log API so the diagram does not depend on a separate `/pools` fetch for Pool labels?

## Lightweight VPS Runtime Goal

Lune v0.1.6 should make small long-running VPS deployments a first-class target.

The target deployment is a 2-core VPS with 2GB or 4GB RAM. The optimized path should preserve the default Codex/CPA experience while reducing unnecessary memory, CPU, disk, and SQLite pressure.

This release should not rewrite the main technical stack. The current Go single-binary service, embedded frontend assets, and SQLite storage model remain appropriate for low-resource deployment. The optimization work should focus on runtime defaults, deployment shape, health-check behavior, logging, and memory pressure.

## Runtime Direction

- Keep Go + SQLite as the primary runtime stack.
- Keep the web frontend as build-time Vite/React assets embedded into the Go binary.
- Do not introduce a Node/Python/Java runtime dependency for production.
- Keep CPA supported by default, because the primary usage pattern is Codex/CPA accounts.
- Do not prioritize CPA on-demand suspend/resume in v0.1.6. The user expects CPA to be used most of the time, so the added complexity and cold-start latency are not justified yet.
- Keep Docker support, but introduce and document native binary/systemd deployment as the recommended small-VPS path.

## Deployment Modes

### Native systemd, recommended for 2C2G

The recommended low-resource deployment should be:

- `/usr/local/bin/lune`
- `/usr/local/lib/lune/CLIProxyAPI`
- `/etc/lune/lune.env`
- `/var/lib/lune/lune.db`
- `/var/lib/lune/cpa-auth/`
- `/var/lib/lune/tmp/`
- `lune.service`

The native bundle should not require Go, Node, npm, or Docker on the target server.

### Docker Compose, retained for convenience

Docker remains supported for users who prefer a single compose workflow or already run Docker on the VPS.

For small VPS documentation, Docker should be positioned as the convenient path, not the lowest-overhead path. If the VPS is dedicated to Lune, Docker adds daemon/container overhead that native deployment avoids.

## Release Artifacts

The release should provide at least:

- `lune-linux-amd64`
- `lune-linux-arm64`
- `lune-bundle-linux-amd64.tar.gz`
- `lune-bundle-linux-arm64.tar.gz`

The bundle artifact should include:

- `bin/lune`
- `bin/CLIProxyAPI`
- example `lune.env`
- example `lune.service`
- an install script for native systemd deployment

The install script should create required directories, install binaries, write example config if absent, install the service file, and leave secrets for the user to set explicitly.

## Low Resource Profile

Add a first-class low-resource profile:

`LUNE_RESOURCE_PROFILE=low`

When enabled, defaults should shift toward lower steady-state overhead and lower memory spikes.

Initial low-resource defaults:

- `LUNE_LOG_LEVEL=warn` unless explicitly overridden.
- `health_check_interval`: 300s or 600s.
- `max_retry_attempts`: 2.
- `gateway_memory_body_mb`: 1MB or 2MB.
- `gateway_max_body_mb`: 20MB to 32MB.
- `data_retention_days`: 7 to 14 days.
- CPA remains enabled/embedded by default.

The profile must not override an explicit user setting from the database or environment. It should only change defaults.

## Go Runtime Recommendations

Native and Docker docs should recommend explicit Go runtime limits for small VPS deployments:

```env
GOMEMLIMIT=256MiB
GOGC=100
```

For 4GB VPS deployments, docs may suggest `GOMEMLIMIT=384MiB` or `512MiB` if the user wants more cache headroom.

These values should be documented as recommendations, not hard-coded into the binary.

## SQLite Resource Optimizations

Configure the SQLite database handle for small-process usage:

- `SetMaxOpenConns(1)`
- `SetMaxIdleConns(1)`
- Keep WAL mode.
- Keep `busy_timeout`.
- Keep foreign keys enabled.

The goal is to reduce idle connection overhead and avoid unnecessary concurrent SQLite writers in a small single-process deployment.

## Health Check Optimization

Health checks should become less aggressive under `LUNE_RESOURCE_PROFILE=low`.

Requirements:

- Low-resource profile should lower health-check concurrency.
- Avoid spawning one goroutine per enabled account before acquiring a semaphore.
- Prefer a bounded worker pool or equivalent fixed-concurrency design.
- Default low-resource concurrency should be 1 to 3 workers.
- Health checks should not dominate idle CPU on systems with many CPA accounts.
- CPA service health checks should remain present, but should not be so frequent that the service is constantly doing background work.

## Request Log and Data Retention Optimization

Request logging currently writes to SQLite for each gateway request. This is useful for Activity, but can become unnecessary write pressure on small VPS deployments.

v0.1.6 should support a lower-overhead logging posture:

- Shorter default retention under the low-resource profile.
- Keep automatic pruning enabled and visible in Settings.
- Consider a setting to record only failed requests or disable detailed Activity logs in a future release.
- Consider a lightweight async write queue or batching in a future release if high request volume becomes a real bottleneck.

For v0.1.6, shortened retention and pruning are the minimum requirement. Async/batched logging can remain a follow-up unless implementation risk is low.

## Request and Response Memory Controls

Request body replay already supports disk spillover. Low-resource mode should use that path earlier.

Requirements:

- Reduce the default memory body threshold under `LUNE_RESOURCE_PROFILE=low`.
- Keep large request replay files in `LUNE_GATEWAY_TMP_DIR`.
- Clean up replay files on startup and request completion.
- Add a maximum non-stream response buffer limit, because non-stream responses are currently read fully into memory before being written to the client.
- Streaming responses should continue to be forwarded incrementally and should not be buffered.

## Large Non-Stream Response Streaming

Large non-stream response handling is in scope for v0.1.6 because it directly supports the lightweight VPS goal.

### Current Problem

Lune currently buffers non-stream upstream responses in memory before writing them to the client.

This is useful for retry behavior and usage parsing, but it can become expensive when upstream providers return large non-stream responses, especially `/v1/responses` image and file workflows.

### Direction

- Keep buffering small non-stream responses in memory.
- Add a configurable response buffer threshold.
- For responses over the threshold, avoid holding the entire response body in memory.
- Prefer direct streaming to the client once Lune has determined the response cannot be retried safely.
- Preserve bounded metadata needed for Activity.
- Preserve usage parsing for small buffered responses.
- For large streamed responses, usage may be unavailable unless it can be parsed from bounded metadata without defeating the memory goal.
- Distinguish response-body streaming from request-body replay-to-disk; they solve different memory problems.

### Retry Semantics

- Retry behavior should remain unchanged for failures that occur before upstream response headers are received.
- Once response headers or body bytes are written to the downstream client, Lune must not retry the request.
- For large non-stream responses that cross the threshold, memory protection is more important than preserving full-body retry after the upstream has already responded.

### Initial Defaults

The exact threshold should be decided during implementation. A reasonable first target:

- Normal profile: 8MB to 16MB.
- Low-resource profile: 1MB to 4MB.

The setting should be global for v0.1.6. Per-route thresholds can remain a future enhancement.

### Test Cases

- Small non-stream JSON response remains buffered and preserves usage parsing.
- Large non-stream JSON response does not allocate the full response body.
- Large non-stream binary/file-like response is forwarded without full buffering.
- Upstream failure before response headers remains retryable.
- Upstream failure after downstream write is not retried and is recorded accurately.
- Activity still records route, status, latency, source kind, and bounded error information.

### Follow-up Questions

- Can usage be parsed from a bounded response tail or side channel for large responses?
- Should specific routes force buffering when retry fidelity matters more than memory?
- Should the threshold eventually be configurable per route?

## External CPA Advanced Mode

External CPA support is in scope for v0.1.6 only as a narrow advanced-mode cleanup. The default product path remains embedded CPA.

### Goal

Keep the all-in-one embedded CPA experience as the default while providing a coherent opt-in path for users who intentionally want to run CPA outside the Lune process/container.

This supports lightweight and advanced deployments where users may want:

- Independent CPA upgrades.
- Custom CPA configuration.
- Existing CPA deployments.
- Separate debugging or operation of CPA.

### Direction

- Default remains embedded CPA.
- External CPA must be opt-in.
- External CPA should be configured with explicit Lune environment variables.
- Documentation should clearly mark this as advanced.
- The default quick start should not lead with external CPA.
- Docker Compose and `.env.example` should expose a coherent external CPA path instead of requiring users to infer it from internal variables.
- Settings should distinguish `embedded` from `external` runtime mode instead of always displaying `embedded`.

### Suggested Configuration Shape

The exact names can be finalized during implementation, but the documented path should answer these questions explicitly:

- How to disable embedded CPA.
- Which CPA base URL Lune should connect to.
- Which API key Lune should use for provider requests.
- Which management key Lune should use for CPA management operations.

Existing variables already point in this direction:

- `LUNE_EMBEDDED_CPA=0`
- `LUNE_CPA_BASE_URL`
- `LUNE_CPA_API_KEY`
- `LUNE_CPA_MANAGEMENT_KEY`

### Minimum Acceptance Criteria

- Embedded CPA remains the default in Docker and native bundle deployments.
- External CPA can be configured without patching internal files.
- Settings reports `external` when Lune is connected to an opt-in external CPA runtime.
- Tests cover embedded vs external runtime-mode detection/config parsing.

### Non-Goals for v0.1.6

- Do not revive a complex old two-container quick start as the default.
- Do not add a migration wizard.
- Do not build CPA on-demand suspend/resume.
- Do not build managed CPA binary updates.

## Managed CPA Update

Managed CPA binary updates are explicitly out of scope for v0.1.6.

This feature would allow Lune to download and run a CPA binary under the data directory independently of the Lune release. It requires trusted release metadata, checksum or signature verification, rollback behavior, update records, UI controls, and careful interaction with container immutability.

The default v0.1.6 path should remain:

- Embedded pinned CPA changes when Lune is upgraded.
- External CPA is available for advanced users who need independent CPA upgrades.
- No silent or automatic CPA binary replacement.

## Docker Low Resource Guidance

Docker support should include low-resource env guidance:

```env
GOMEMLIMIT=256MiB
GOGC=100
LUNE_RESOURCE_PROFILE=low
LUNE_LOG_LEVEL=warn
```

Compose docs may include a memory limit example:

```yaml
deploy:
  resources:
    limits:
      memory: 768M
```

This is advisory. The service must still function without Docker-specific resource controls.

## Expected Resource Targets

These are design targets, not guaranteed measurements. v0.1.6 should include real measurements once tested on a small VPS.

| Mode | Idle memory target | Active request target | Idle CPU target |
| --- | ---: | ---: | --- |
| Native Lune only | 40-100MB | 80-200MB | Near 0 |
| Native Lune + CPA | 150-400MB | 250-700MB | Near 0 except checks |
| Docker Lune + CPA, no existing Docker daemon | 300-700MB | 400MB-1GB | Near 0 except checks |
| Docker Lune + CPA, existing Docker host | Native plus smaller marginal overhead | Similar to native plus overhead | Near 0 except checks |

2C2G should be supported with native `lune + CPA` and the low-resource profile. Docker on 2C2G should be supported but documented as having less headroom. 2C4G should be comfortable with either native or Docker deployment.

## Lightweight Runtime Acceptance Criteria

- A native bundle can install Lune with embedded CPA support without Docker.
- `LUNE_RESOURCE_PROFILE=low` changes defaults without overwriting explicit user configuration.
- SQLite connection pool limits are applied.
- Health-check concurrency and interval are lower in low-resource mode.
- Request body memory threshold is lower in low-resource mode.
- Default log verbosity is lower in low-resource mode.
- Docs clearly distinguish native/systemd as the recommended low-resource path and Docker as the convenience path.
- Docs include `GOMEMLIMIT`, `GOGC`, and expected memory target guidance.

## 待解决问题：CPA 登录态误判与凭据生命周期

2026-05-07 的生产事件暴露出 CPA 账号状态判断和凭据管理上的问题。以下问题进入 v0.1.6 待解决清单：

- [ ] Codex quota 辅助接口 `wham/usage` 返回 `401/403` 时，不应直接把整个 CPA 账号标记为 `needs_login`。需要区分 quota 获取失败、订阅/额度元数据失败和真实登录态失效。
- [ ] `cpa_credential_status` 的语义过载：当前同时表达真实凭据失效、CPA runtime 异常、auth index 同步中、quota 接口失败等状态。需要拆分或补充字段，让前端能准确展示问题来源。
- [ ] CPA 凭据状态可能被不同路径来回覆盖：网关模型请求成功会标记 `ok`，后台 quota 刷新失败又可能标记 `needs_login`。需要定义状态优先级和写入规则，避免 UI 在“可用”和“需要重新登录”之间抖动。
- [ ] 删除 CPA 账号时只删除数据库 `accounts` 记录，不清理 `/app/data/cpa-auth/<accountKey>.json`。需要决定删除语义：同步删除 auth 文件、提供保留选项，或至少在 UI 中明确提示凭据文件会残留。
- [ ] 登录态/额度刷新相关日志缺少审计信息。需要记录安全的状态迁移摘要，包括账号 ID、account key、失败接口类型、HTTP 状态、credential 状态前后值和归一化 reason，避免事后只能从零散日志推断。
- [ ] 前端“需要重新登录”提示过于绝对。需要根据后端 reason 展示更细的提示，例如“额度获取失败”“订阅元数据获取失败”“CPA runtime 异常”“凭据同步中”或“确需重新登录”。
