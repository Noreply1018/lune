## Current Problem

Lune currently forwards streaming responses directly to the client and treats the stream as finished when the response body reader ends.

This misses several failure modes:

- The upstream stream closes before `[DONE]` or `response.completed`.
- The upstream stream emits a semantic failure event such as `response.failed`.
- The upstream read fails after response headers have already been written.
- A large SSE line exceeds the current scanner limit.
- Writing to the downstream client fails mid-stream.
- The gateway request timeout terminates a long stream.

In these cases, client SDKs can report errors such as:

`stream disconnected before completion: stream closed before response.completed`

Another observed example is an upstream capacity failure surfaced by the client:

`Selected model is at capacity. Please try a different model`

Activity may still show the request as successful because the stream forwarding path does not return read/write/completion errors to the gateway handler.

## Capacity Failure Semantics

The message `Selected model is at capacity. Please try a different model` is not generated by Lune. It is an upstream model/account capacity failure surfaced through the client protocol.

Lune's responsibility is to avoid misclassifying that request as successful:

- If the capacity failure arrives before response headers or stream bytes are sent, normal retry may still be possible.
- If the capacity failure arrives after stream output has started, Lune should not retry because the downstream response is already committed.
- In both cases, Activity should record the routed pool/account/model and the upstream capacity message.
- A stream-level capacity failure should not clear an existing account error state or mark the account healthy just because the HTTP status was `200`.

## Lightweight VPS Runtime Goal

Lune v0.1.6 should make small long-running VPS deployments a first-class target.

The target deployment is a 2-core VPS with 2GB or 4GB RAM. The optimized path should preserve the default Codex/CPA experience while reducing unnecessary memory, CPU, disk, and SQLite pressure.

This release should not rewrite the main technical stack. The current Go single-binary service, embedded frontend assets, and SQLite storage model remain appropriate for low-resource deployment. The optimization work should focus on runtime defaults, deployment shape, health-check behavior, logging, and memory pressure.

## Runtime Direction

- Keep Go + SQLite as the primary runtime stack.
- Keep the web frontend as build-time Vite/React assets embedded into the Go binary.
- Do not introduce a Node/Python/Java runtime dependency for production.
- Keep CPA supported by default, because the primary usage pattern is Codex/CPA accounts.
- Do not prioritize CPA on-demand suspend/resume in v0.1.6. The user expects CPA to be used most of the time, so the added complexity and cold-start latency are not justified yet.
- Keep Docker support, but introduce and document native binary/systemd deployment as the recommended small-VPS path.

## Deployment Modes

### Native systemd, recommended for 2C2G

The recommended low-resource deployment should be:

- `/usr/local/bin/lune`
- `/usr/local/lib/lune/CLIProxyAPI`
- `/etc/lune/lune.env`
- `/var/lib/lune/lune.db`
- `/var/lib/lune/cpa-auth/`
- `/var/lib/lune/tmp/`
- `lune.service`

The native bundle should not require Go, Node, npm, or Docker on the target server.

### Docker Compose, retained for convenience

Docker remains supported for users who prefer a single compose workflow or already run Docker on the VPS.

For small VPS documentation, Docker should be positioned as the convenient path, not the lowest-overhead path. If the VPS is dedicated to Lune, Docker adds daemon/container overhead that native deployment avoids.

## Low Resource Profile

Add a first-class low-resource profile:

`LUNE_RESOURCE_PROFILE=low`

When enabled, defaults should shift toward lower steady-state overhead and lower memory spikes.

Initial low-resource defaults:

- `LUNE_LOG_LEVEL=warn` unless explicitly overridden.
- `health_check_interval`: 300s or 600s.
- `max_retry_attempts`: 2.
- `gateway_memory_body_mb`: 1MB or 2MB.
- `gateway_max_body_mb`: 20MB to 32MB.
- `data_retention_days`: 7 to 14 days.
- CPA remains enabled/embedded by default.

The profile must not override an explicit user setting from the database or environment. It should only change defaults.

## Go Runtime Recommendations

Native and Docker docs should recommend explicit Go runtime limits for small VPS deployments:

```env
GOMEMLIMIT=256MiB
GOGC=100
```

For 4GB VPS deployments, docs may suggest `GOMEMLIMIT=384MiB` or `512MiB` if the user wants more cache headroom.

These values should be documented as recommendations, not hard-coded into the binary.

## SQLite Resource Optimizations

Configure the SQLite database handle for small-process usage:

- `SetMaxOpenConns(1)`
- `SetMaxIdleConns(1)`
- Keep WAL mode.
- Keep `busy_timeout`.
- Keep foreign keys enabled.

The goal is to reduce idle connection overhead and avoid unnecessary concurrent SQLite writers in a small single-process deployment.

## Health Check Optimization

Health checks should become less aggressive under `LUNE_RESOURCE_PROFILE=low`.

Requirements:

- Low-resource profile should lower health-check concurrency.
- Avoid spawning one goroutine per enabled account before acquiring a semaphore.
- Prefer a bounded worker pool or equivalent fixed-concurrency design.
- Default low-resource concurrency should be 1 to 3 workers.
- Health checks should not dominate idle CPU on systems with many CPA accounts.
- CPA service health checks should remain present, but should not be so frequent that the service is constantly doing background work.

## Request Log and Data Retention Optimization

Request logging currently writes to SQLite for each gateway request. This is useful for Activity, but can become unnecessary write pressure on small VPS deployments.

v0.1.6 should support a lower-overhead logging posture:

- Shorter default retention under the low-resource profile.
- Keep automatic pruning enabled and visible in Settings.
- Consider a setting to record only failed requests or disable detailed Activity logs in a future release.
- Consider a lightweight async write queue or batching in a future release if high request volume becomes a real bottleneck.

For v0.1.6, shortened retention and pruning are the minimum requirement. Async/batched logging can remain a follow-up unless implementation risk is low.

## Request and Response Memory Controls

Request body replay already supports disk spillover. Low-resource mode should use that path earlier.

Requirements:

- Reduce the default memory body threshold under `LUNE_RESOURCE_PROFILE=low`.
- Keep large request replay files in `LUNE_GATEWAY_TMP_DIR`.
- Clean up replay files on startup and request completion.
- Add a maximum non-stream response buffer limit, because non-stream responses are currently read fully into memory before being written to the client.
- Streaming responses should continue to be forwarded incrementally and should not be buffered.

## Large Non-Stream Response Streaming

Large non-stream response handling is in scope for v0.1.6 because it directly supports the lightweight VPS goal.

### Current Problem

Lune currently buffers non-stream upstream responses in memory before writing them to the client.

This is useful for retry behavior and usage parsing, but it can become expensive when upstream providers return large non-stream responses, especially `/v1/responses` image and file workflows.

### Direction

- Keep buffering small non-stream responses in memory.
- Add a configurable response buffer threshold.
- For responses over the threshold, avoid holding the entire response body in memory.
- Prefer direct streaming to the client once Lune has determined the response cannot be retried safely.
- Preserve bounded metadata needed for Activity.
- Preserve usage parsing for small buffered responses.
- For large streamed responses, usage may be unavailable unless it can be parsed from bounded metadata without defeating the memory goal.
- Distinguish response-body streaming from request-body replay-to-disk; they solve different memory problems.

### Retry Semantics

- Retry behavior should remain unchanged for failures that occur before upstream response headers are received.
- Once response headers or body bytes are written to the downstream client, Lune must not retry the request.
- For large non-stream responses that cross the threshold, memory protection is more important than preserving full-body retry after the upstream has already responded.

### Initial Defaults

The exact threshold should be decided during implementation. A reasonable first target:

- Normal profile: 8MB to 16MB.
- Low-resource profile: 1MB to 4MB.

The setting should be global for v0.1.6. Per-route thresholds can remain a future enhancement.

### Test Cases

- Small non-stream JSON response remains buffered and preserves usage parsing.
- Large non-stream JSON response does not allocate the full response body.
- Large non-stream binary/file-like response is forwarded without full buffering.
- Upstream failure before response headers remains retryable.
- Upstream failure after downstream write is not retried and is recorded accurately.
- Activity still records route, status, latency, source kind, and bounded error information.

### Follow-up Questions

- Can usage be parsed from a bounded response tail or side channel for large responses?
- Should specific routes force buffering when retry fidelity matters more than memory?
- Should the threshold eventually be configurable per route?

## External CPA Advanced Mode

External CPA support is in scope for v0.1.6 only as a narrow advanced-mode cleanup. The default product path remains embedded CPA.

### Goal

Keep the all-in-one embedded CPA experience as the default while providing a coherent opt-in path for users who intentionally want to run CPA outside the Lune process/container.

This supports lightweight and advanced deployments where users may want:

- Independent CPA upgrades.
- Custom CPA configuration.
- Existing CPA deployments.
- Separate debugging or operation of CPA.

### Direction

- Default remains embedded CPA.
- External CPA must be opt-in.
- External CPA should be configured with explicit Lune environment variables.
- Documentation should clearly mark this as advanced.
- The default quick start should not lead with external CPA.
- Docker Compose and `.env.example` should expose a coherent external CPA path instead of requiring users to infer it from internal variables.
- Settings should distinguish `embedded` from `external` runtime mode instead of always displaying `embedded`.

### Suggested Configuration Shape

The exact names can be finalized during implementation, but the documented path should answer these questions explicitly:

- How to disable embedded CPA.
- Which CPA base URL Lune should connect to.
- Which API key Lune should use for provider requests.
- Which management key Lune should use for CPA management operations.

Existing variables already point in this direction:

- `LUNE_EMBEDDED_CPA=0`
- `LUNE_CPA_BASE_URL`
- `LUNE_CPA_API_KEY`
- `LUNE_CPA_MANAGEMENT_KEY`

### Minimum Acceptance Criteria

- Embedded CPA remains the default in Docker and native bundle deployments.
- External CPA can be configured without patching internal files.
- Settings reports `external` when Lune is connected to an opt-in external CPA runtime.
- Tests cover embedded vs external runtime-mode detection/config parsing.

### Non-Goals for v0.1.6

- Do not revive a complex old two-container quick start as the default.
- Do not add a migration wizard.
- Do not build CPA on-demand suspend/resume.
- Do not build managed CPA binary updates.

## Managed CPA Update

Managed CPA binary updates are explicitly out of scope for v0.1.6.

This feature would allow Lune to download and run a CPA binary under the data directory independently of the Lune release. It requires trusted release metadata, checksum or signature verification, rollback behavior, update records, UI controls, and careful interaction with container immutability.

The default v0.1.6 path should remain:

- Embedded pinned CPA changes when Lune is upgraded.
- External CPA is available for advanced users who need independent CPA upgrades.
- No silent or automatic CPA binary replacement.

- 两条记录都挂在同一个 Pool。
- request log 显示 `id=6` 在 `2026-05-10 11:52-11:54` 期间连续服务 `gpt-5.5` 且 HTTP 200。
- `id=8` 的失败状态来自后台 Codex quota 刷新路径调用 `https://chatgpt.com/backend-api/wham/usage`，不是网页登录失败，也不是普通模型生成请求失败。

当时最快的运行侧修复是保留健康的 `id=6`，删除或禁用重复失败的 `id=8`。删除账号行会通过外键级联移除它的 Pool membership；如果只想降低即时路由风险，应优先禁用重复账号或从 Pool 移除。

### 事件二：删除重复账号后重新登录仍显示需要重新登录

用户随后删除了两个 `r` 账号并重新添加同一账号，但新账号仍显示 `needs_login`。第二次审计发现这已经不是重复账号残留，而是同名 CPA auth 文件和 embedded CPA runtime auth index 的生命周期问题。

关键时间线：

- `2026-05-10 12:10:27` 删除旧 `id=6`。
- `2026-05-10 12:10:41` 删除旧 `id=8`。
- `2026-05-10 12:10:50` 开始新的 CPA Device Code 登录。
- `2026-05-10 12:11:38` 新登录成功，登录会话里的账号对象显示 `cpa_last_refresh_at=2026-05-10T12:11:38Z`。
- `2026-05-10 12:11:39` 登录收尾阶段第一次 quota 刷新立刻返回 `HTTP 401`，日志为 `finalizeLogin: initial CPA refresh incomplete account_id=8 err="HTTP 401"`。
- 随后后台持续出现 `fetch codex quota account_id=8 err="HTTP 401"`。
- 当前磁盘 auth 文件 `/app/data/cpa-auth/codex-rebeccanicholson4700@outlook.com-plus.json` 又显示 `last_refresh=2026-05-10T08:01:42Z`，DB 也被同步回这个旧值。

### 根因判断

v0.1.5 的 embedded CPA 集成存在同名凭据重登缺陷：

1. 删除 CPA 账号只删除 DB `accounts` 行，不删除同名 auth file，也不通知 embedded CPA runtime 释放或重载旧 auth index。
2. 重新 Device Code 登录会覆盖同名 auth file，但不会无条件重启或 reload embedded CPA runtime。
3. `resolveAuthMetadata` 只要从 CPA management `/auth-files` 看到同 key 已存在 `auth_index`，就直接复用；它不校验这个 auth index 对应的 runtime 内存凭据是否与磁盘新 token 一致。
4. 如果 CPA runtime 仍持有旧内存 auth entry，后续 quota `api-call` 会继续用旧 token 访问 `wham/usage`，返回 HTTP 401。
5. quota 401 被 Lune 写成 `cpa_credential_status=needs_login`，所以 UI 显示“需要重新登录”。
6. 如果 CPA runtime 又把旧内存凭据落回同名 auth file，Lune 的 `resolveCpaRuntime` / `syncCpaMetadata` 会无条件读取磁盘文件并把旧 `expired/last_refresh` 写回 DB。

这说明“网页可登录”与“Lune/CPA 本地凭据可用”是两个独立事实。网页登录成功不能证明 embedded CPA runtime 当前使用的是刚登录的新 token。

### v0.1.6 设计修复方向

- [x] 对 CPA 账号增加数据库唯一性约束：对 `source_kind='cpa' AND cpa_service_id IS NOT NULL AND cpa_account_key <> ''` 的记录建立 `UNIQUE(cpa_service_id, cpa_account_key)`。
- [x] 增加迁移前重复检测。若已有重复 CPA key，迁移应输出可诊断信息，不能静默创建索引失败。
- [x] 所有 CPA 导入路径必须幂等：Device Code 登录、远程单账号导入、批量导入都应复用同一个 upsert 逻辑。
- [x] 同一 `cpa_account_key` 重新登录时，应更新已有账号和 Pool membership，而不是创建重复账号。
- [x] Pool attach 必须幂等：已有账号加入已有 Pool 时不应创建新账号，也不应产生用户不可见的重复状态。
- [ ] 删除 CPA 账号时必须明确凭据文件语义：删除 auth file、保留 auth file、或给用户显式选项。无论哪种策略，都必须在 UI/API 文案中明确。
- [~] 删除、覆盖或重新登录同名 CPA auth file 后，embedded CPA runtime 必须强制 reload 或重启，不能只在 auth index 缺失时才触发 reload。已完成覆盖/重新登录后的 reload；删除语义仍待单独设计。
- [x] `resolveAuthMetadata` 不应只以“存在 auth index”为 ready 条件。它应校验 runtime metadata 与磁盘 auth file 的关键版本信息，例如 account key、OpenAI account id、last_refresh、文件 mtime 或 token 指纹。
- [x] 如果同名 auth file 被新 token 覆盖，但 runtime 仍返回旧 auth index，应触发 CPA reload，并在 reload 后重新读取 auth metadata。
- [x] `syncCpaMetadata` / `resolveCpaRuntime` 从磁盘 auth file 写回 DB 时，应防止旧 metadata 覆盖更新后的登录状态。至少需要基于 `last_refresh` 或单调版本做新旧比较。
- [x] 登录完成后的首次 refresh 如果 quota 失败，不应立即把刚登录账号定性为 `needs_login`。应区分“quota 获取失败”和“凭据确需重新登录”。
- [x] Codex quota HTTP 401 应优先写入 `quota_status` / `quota_last_error`。只有 refresh token 明确失效、auth file 缺失/损坏、CPA runtime 明确要求重新认证，或多个鉴权敏感探针一致失败时，才升级为 `credential_status=needs_login`。
- [ ] UI 应增加重复账号检测：当多个启用账号拥有相同 `(cpa_service_id, cpa_account_key)` 时，显示“重复导入”并提供安全清理入口。
- [x] UI 文案应区分“需要重新登录”和“额度查询失败”。浏览器登录正常但本地 CPA 凭据异常时，应解释两者不是同一个登录态。
- [ ] 登录、删除、reload、metadata sync 和 quota refresh 应写入安全审计日志，记录 account id、account key、auth file version、runtime auth index、状态前后值和失败来源。

### 最小测试要求

- [x] Device Code 登录同一个已存在 CPA account key 时，更新现有账号，不创建重复账号。
- [ ] 删除 CPA 账号后重新登录同一个 account key，embedded CPA runtime 使用新 token；首次 quota refresh 不应继续使用旧 auth index。
- [x] 同名 auth file 被覆盖后，`resolveAuthMetadata` 能检测 runtime metadata 与磁盘 metadata 不一致并触发 reload。
- [x] `syncCpaMetadata` 不会用旧 `last_refresh` 覆盖更新后的 DB 登录状态。
- [x] batch import 遇到已存在 CPA account key 时跳过或更新，不创建重复账号。
- [x] quota HTTP 401 不会在普通模型请求仍健康时单独把账号展示为“需要重新登录”。
- [x] 重复 CPA account key 出现在数据库中时，迁移或启动检查能给出明确诊断。

## 2026-05-11 生产审计：CPA provider 级转发导致账号归属错位

本节来自 `noreply1018/lune:0.1.5` 容器的只读生产审计。用户现象是：Lune 前端几乎所有请求量都显示在 Pool 序列第一的 Codex CPA 账号上，但后续其他 Codex 账号的远端额度却持续减少。

### 现象确认

审计快照中，`request_logs` 的请求归属高度集中在账号 1：

- account `id=1`：约 499 条请求。
- account `id=2/3`：各约 4 条请求。
- account `id=4/5`：各约 3 条请求。
- 绝大多数近期 `POST /v1/responses` 日志都记录为 `account_id=1`，且 `attempt_count=1`。

但各账号的 `codex_quota_json` 都包含与账号自身匹配的远端 email，且后续账号的 quota 快照显示真实额度消耗：

- account `id=2` 的 quota email 为 `cartercabrerazwu@mail.com`，5h 窗口已用 `100%`，7d 窗口约 `76%`。
- account `id=5` 的 quota email 为 `lrej71853@outlook.com`，5h 窗口已用 `100%`，7d 窗口约 `16%`。

这说明前端不是简单把第一个账号的 quota 画到后续账号上；证据高度支持后续账号对应的 Codex 凭据也被同一 CPA 凭据链路使用过。错位发生在“Lune 记录的 account row”和“CPA runtime 实际选用的 Codex auth file”之间。

### 根因

v0.1.5 的普通 CPA 网关链路是两层独立调度：

`client -> Lune router 选 accounts.id -> Lune 记录 request_logs.account_id -> /api/provider/codex/v1 -> CPA runtime 自行选择 Codex auth file`

Lune 第一层调度会按 Pool member 顺序选择 Lune account，并把该 `resolved.AccountID` 写入 `request_logs.account_id`。这条日志只表示“Lune 认为自己选中了哪个账号行”。

但是转发到 CPA 时，v0.1.5 只使用 provider 级地址：

`{cpa_base_url}/api/provider/{cpa_provider}/v1`

对多个 Codex CPA account 来说，`cpa_provider` 都是 `codex`，所以它们的上游 URL 完全相同。转发请求没有携带 `cpa_account_key`、CPA `auth_index`、email、OpenAI account id 或任何能够 pin 到某个 auth file 的字段。

CPA v6.9.41 的 `/api/provider/codex/v1/...` provider endpoint 也不会从公开 HTTP header/query/body 中读取 `auth_index` 来绑定账号。Lune entrypoint 生成的内置 CPA 配置没有设置 `routing.strategy`；未绑定且未覆盖策略时，CPA 会落到自身默认 selector，在所有可用 Codex auth file 中 round-robin 选择凭据。这不是 Lune 的 Pool 顺序，也不是 Lune 的 `account_id`。

因此，Lune 可以持续把请求日志记到账号 1，而 CPA 实际轮询使用账号 2/3/4/5 的 Codex 凭据，导致后续账号额度减少。

### 代码证据

Lune v0.1.5 侧：

- `internal/router/router.go` 只返回 `ResolvedRoute{PoolID, TargetModel, AccountID, Account}`，选择的是 Lune account row，不是 CPA auth file。
- `internal/gateway/handler.go` 的 `resolveTarget` 对 CPA 账号只拼 `/api/provider/{provider}/v1`，并只携带 CPA service API key 与 Lune `account.ID`。
- `internal/gateway/proxy.go` 的 `UpstreamTarget` 只有 `BaseURL/APIKey/AccountID`，没有 `CpaAccountKey`、`AuthIndex` 或 runtime credential id。
- `internal/gateway/proxy.go` 转发时只替换 `Authorization: Bearer <CPA API key>`；`X-Lune-Account-Id` 只被 Lune 用作强制路由输入。即使该 header 随普通 header 复制被原样转发给 CPA，Lune 也没有把它转换成 CPA 可识别的 credential pinning 参数，CPA 不会把它当作选择 auth file 的依据。
- `internal/gateway/handler.go` 的 `logRequest` 从 `resolved.AccountID` 写入 `request_logs.account_id`。
- `internal/store/logs.go` 只持久化该 `account_id`，没有保存实际 CPA auth id / auth index。

CPA v6.9.41 侧：

- Dockerfile 固定内置 CPA 为 `eceasy/cli-proxy-api:v6.9.41`。
- Lune entrypoint 生成的 CPA `config.yaml` 只包含 `port`、`auth-dir`、management key 和 API key，没有账号绑定配置，也没有 `routing.strategy` 覆盖。
- Lune 内置 CPA 配置未设置 `routing.strategy`，因此落到 CPA 默认 `RoundRobinSelector`；只有显式 `routing.strategy=fill-first` 才会改为 fill-first。
- CPA provider route `/api/provider/:provider/v1/...` 只是 provider alias。实际 auth pool 由请求模型解析和 CPA 内部 auth manager 决定。
- CPA 的 `auth_index` 主要用于 management API `/v0/management/api-call`，不是普通 provider 转发路径的公开绑定参数。

### 与重试问题的区别

Lune 自身也有跨账号重试：非强制账号请求遇到网络错误、HTTP 429 或 5xx 时，可能排除当前账号并选择下一个 Pool member。

但本次生产快照中绝大多数请求 `attempt_count=1`，只有极少数多尝试记录。因此这不是“Lune 重试后把后续账号错记为第一个”的主要问题。

本问题的本质是：**Lune 日志账号归属和 CPA runtime 凭据归属没有协议级绑定**。

### v0.1.6 修复方向

- [ ] 普通 CPA 网关请求必须能绑定到 Lune account 对应的 CPA credential。绑定键应来自可靠的 runtime 身份，例如 CPA auth id / `auth_index` / `cpa_account_key` 映射，而不能只用 provider 名。
- [ ] `resolveCpaRuntime` 获取到的 runtime auth metadata 不能只服务于 quota/subscription 刷新；普通模型转发也必须能使用同一份已校验 metadata。
- [ ] 如果 CPA 当前 provider endpoint 不支持公开 pinning 参数，应优先推动或适配 CPA 的 pinned auth 能力；否则 Lune 不能声称支持同一个 CPA runtime 下多个 Codex account 的准确账号级路由与统计。
- [ ] `request_logs` 应记录两类身份：`account_id` 表示 Lune 选择的账号行；`runtime_auth_id` 或 `runtime_auth_index` 表示 CPA 实际执行凭据。没有实际凭据回传时，应明确标记为 `unknown`，避免 Activity 暗示账号归属精确。
- [ ] Activity / Pool 详情页应区分“Lune routed account”和“CPA actual credential”。在无法确认实际凭据时，账号级请求统计必须降级提示，而不是给出看似精确的账号请求量。
- [ ] 对 CPA provider 转发路径增加诊断日志：记录 request_id、Lune account id、cpa_account_key、runtime auth index、CPA selected auth id、模型、状态码和安全截断后的错误信息。
- [ ] 外部 CPA advanced mode 文档必须说明：如果多个 Lune CPA account 共用同一个外部 CPA runtime，而该 runtime 不支持 per-request credential pinning，则账号级统计和额度归因不可信。
- [ ] 当前工作树已有的 routability、quota blocked、重复 account key、auth metadata mismatch 修复仍然必要，但它们不能替代普通模型请求的 credential pinning。

### v0.1.6 验收标准

- [ ] 在同一个 CPA runtime 中导入 3 个 Codex auth file 后，通过强制路由或固定 Pool 选择器稳定命中第一个 Lune CPA account，并控制重试不切换账号；连续发起 10 次普通模型请求时，实际 CPA selected auth 必须全部等于该 Lune account 对应凭据，后续账号远端 quota 不应被消耗。
- [ ] 强制路由 `X-Lune-Account-Id` 指向某个 CPA account 时，CPA 实际 selected auth 必须等于该 account 对应凭据；否则请求应 fail closed，不得静默使用其他账号。
- [ ] 普通 Pool 自动路由选择第 N 个 CPA account 时，`request_logs.account_id` 与 `runtime_auth_id/runtime_auth_index` 能够一一对应并可审计。
- [ ] 当 CPA runtime 不支持 credential pinning 或 auth metadata 未就绪时，该账号不可接普通流量，错误信息应明确为 `runtime_auth_binding_unavailable` 或等价 reason。
- [ ] Activity 页面展示的账号请求量必须基于已确认的 runtime credential 归属；无法确认时显示不确定状态，而不是把请求全部归到 Lune 首选账号。
- [ ] 单元测试覆盖：CPA target 构建必须携带 runtime credential binding；缺失 binding 时 fail closed；日志同时保存 Lune account id 与 runtime auth id。
- [ ] 集成测试覆盖：模拟 CPA round-robin runtime，验证 Lune pinning 后不会被 CPA 默认 round-robin 打散。

- 账号 2、3、5 均处于 Pool 启用成员列表中，路由仍可选择这些账号。

容器运维状态也与仓库 compose 不一致：

- 当前容器 `RestartPolicy=no`，没有 Docker healthcheck。
- 当前端口绑定为 `0.0.0.0:11111->7788`，而仓库 compose 期望绑定 `127.0.0.1`。这不是单纯部署差异；如果管理端鉴权继续信任 private IP，同一内网来源可能绕过 admin token。
- 当前数据卷是宿主机 bind mount `C:\Users\lh\lune-data:/app/data`，而仓库 compose 使用 named volume。
- 当前 Docker json-file 日志没有 `max-size` / `max-file` 上限。
- CPA 与 Lune 在同一容器内以后台子进程方式运行，入口脚本只等待 `lune up`，没有严格监督 CPA 子进程。

### 根因

1. `status`、`cpa_credential_status`、订阅状态、额度状态是并行状态，但路由主要只依赖账号 `status=healthy/degraded`。
2. 健康检查用 `/v1/models` 判定账号 healthy，不能证明生成请求、Codex quota、订阅、ChatGPT 账号权限仍可用。
3. 网关和后台刷新会异步写入账号状态，最后写入胜出。一次成功请求可能把凭据标为 `ok`，后台 quota 401 又可能把它标为 `needs_login`。
4. `401/403` 以及包含 `unauthorized/access denied/expired token/refresh token` 的文本被过宽地归类为登录态失效，可能把额度、订阅、权限、上游临时拒绝误判成“需要重新登录”。
5. 缺少 per-account、per-error、per-token 的失败窗口、冷却期、自动隔离和自动禁用机制。错误账号会被反复尝试。
6. 请求日志和 stdout 日志是逐请求写入，没有重复错误聚合、采样、限速或磁盘上限。
7. 订阅和额度刷新只有成功时间或旧快照，没有完整的 `last_attempt_at`、`last_success_at`、`last_error`、`status` 状态机，导致 UI 无法可靠解释“滞后”。

### v0.1.6 解决方案

本节是对前述 CPA 登录态问题的运行侧补充，重点把凭据、额度、订阅、路由可用性拆成独立但可组合的状态。

- [ ] 字段迁移：现有 `cpa_credential_status` 在 v0.1.6 迁移为 `credential_status`。旧字段只作为兼容别名读取，不再承载 quota、subscription 或 serving 阻断原因，也不得继续作为后台刷新写入目标。
- [x] 增加账号级 serving 熔断状态：`serving_status`、`failure_count`、`last_failure_at`、`last_success_at`、`cooldown_until`。网关失败应进入冷却窗口，路由在冷却期内跳过该账号。
- [x] 健康检查拆分 discovery health 与 serving health。`/v1/models` 成功只能更新模型发现或 discovery 状态，不能直接清除网关 serving error 或冷却状态。
- [ ] 路由选择必须同时检查账号启用状态、Pool member 启用状态、`serving_status`、`credential_status`、`subscription_status` 和 `quota_status`。任何维度不可接流量时，普通路由都必须跳过该账号。
- [~] 强制账号路由 `X-Lune-Account-Id` 也必须遵守不可接流量状态。只有显式诊断或管理员探测接口可以绕过普通路由限制，且诊断请求应单独标记，不影响普通路由健康。已完成普通强制路由不可绕过；独立诊断入口仍待后续补齐。
- [ ] 拆分四类状态：`credential_status` 只表达凭据、登录态和 CPA runtime；`quota_status` 表达额度；`subscription_status` 表达订阅；`serving_status` 表达网关生成请求维度的短期服务能力与熔断状态。整体是否可接普通流量必须由这四类状态组合计算，不能由 `serving_status` 单独代表。
- [ ] 强化 CPA 凭据状态机。建议 credential 状态至少区分：`ok`、`auth_suspect`、`needs_login`、`refresh_failed`、`runtime_pending`、`runtime_error`、`unknown`。额度和订阅阻断不得重新塞回 credential 字段。
- [x] 缩窄 `needs_login` 判定。不要仅凭任意 `403` 或宽泛文本写入 `needs_login`；只有明确 refresh token 无效、登录态吊销、凭据文件缺失/损坏、CPA 明确要求重新认证时才进入 `needs_login`。
- [ ] 增加状态写入优先级和版本语义。后台刷新失败不能无条件覆盖更新后的成功状态；同一个账号的 credential/serving/quota/subscription 写入应记录来源、前值、后值和时间。
- [ ] 订阅刷新拆分 `subscription_last_attempt_at` 与 `subscription_last_success_at`。metadata pending 或刷新失败时不得把 `last_success_at` 当作成功刷新更新。
- [ ] 增加显式订阅状态：`subscription_status=active|expired|free|unknown|pending|error`，并保留 `plan_type`。Free/无订阅不能只靠空 `expires_at` 推断。
- [ ] quota 缓存增加 `quota_status`、`quota_last_attempt_at`、`quota_last_success_at`、`quota_last_error`。旧 quota 快照旁必须展示“最后成功刷新时间”和“最后尝试失败原因”。
- [ ] 将 `codex_quota_fetch_interval` 接入 settings response、前端类型、Settings 页面控件和 quota stale 计算，并让前端使用后端配置，而不是固定 15 分钟。
- [x] 当 quota 快照显示 `allowed=false` 或 `limit_reached=true` 时，应设置 `quota_status=blocked`，持续到 quota 刷新恢复。`serving_status=cooldown` 只用于上游 5xx、timeout、EOF 等短期失败窗口，两者独立生效。
- [ ] 请求日志增加重复错误折叠。建议按 `time_bucket + token + pool + account + model + status_code + normalized_error` 聚合，记录 `count`、首末时间、样例 request_id。
- [ ] stdout access log 增加降噪配置。默认生产只记录 warn/error、慢请求或采样后的成功请求；高频 admin 轮询和静态资源请求不应刷屏。
- [ ] Activity/Usage API 限制 `page_size` / `limit` 上限，并为常用过滤字段增加索引，避免日志爆量后管理页反过来拖垮实例。
- [x] token 认证必须检查 `access_tokens.enabled`。禁用 token 应拒绝请求；后续可在此基础上增加 per-token QPS 与错误率熔断。
- [ ] 通知去重应覆盖 failed/dropped，不只看近期成功投递。长期故障进入 dropped 后也应有冷却期，避免健康检查下一轮重新入队。
- [ ] 错误日志不得默认保存完整 prompt/request body。CPA/Lune 诊断日志应默认保存脱敏摘要、request_id、账号 ID、状态码、归一化错误和有限长度上游 message。
- [ ] `request_logs.error_message` 应保留安全的上游错误细节，避免所有 CPA 错误都变成 `upstream error`。

### v0.1.6 验收标准

- [x] 当某个 CPA Codex 账号连续产生 5xx/503/EOF/timeout 时，后续独立请求会在冷却期内自动绕过该账号。

- [ ] 当账号状态同时存在 credential 错误和 discovery healthy 信号时，前端展示应明确区分“模型发现正常”和“当前不可接流量原因”。
