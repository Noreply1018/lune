# 03. 0.1.6 容器 CPA Pinning 运行时审计

状态：draft

来源：2026-05-16 对正在运行的 `lune-0.1.5` 与 `lune-0.1.6` 容器进行只读审计。用户反馈 0.1.5 中同来源账号可用，0.1.6 中直连账号与 CPA 账号都不可用；排查过程中一度怀疑 0.1.6 没有设置 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED=1`，需要在真实容器和临时容器中复核。

## 问题

v0.1.6 引入了 CPA runtime credential pinning 和 fail-closed 路由。CPA 账号能否接普通流量，不再只取决于账号是否启用，还取决于 Lune 是否认为当前 CPA provider endpoint 支持逐请求 pinning。

这使排障多了一层容易混淆的启动时状态：

- `docker inspect` 只能看到镜像配置和 `docker run` 传入的静态环境变量。
- PID1 是 `sh /usr/local/bin/lune-entrypoint up`，它的环境不等于后续 `export` 后启动的子进程环境。
- 真正读取 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED` 的是 `lune up` 进程。
- 真正执行 provider 请求的是 embedded `CLIProxyAPI` 子进程。

如果只看 `docker inspect` 或 PID1 环境，会误以为 0.1.6 没有设置 pinning 能力，从而把“账号不可用”的根因错误归到环境变量缺失。

## 审计过程

本次审计遵守只读原则，没有修改正在运行的容器、数据库、auth file 或配置。

### 1. 运行中容器概况

正在运行的两个容器：

- `lune-0.1.5`：镜像 `noreply1018/lune:0.1.5`，embedded CPA 版本 `v6.9.41`。
- `lune-0.1.6`：镜像 `noreply1018/lune:0.1.6`，embedded CPA 版本 `v7.0.2-lune.1`。

静态容器配置中，`lune-0.1.6` 的 `Config.Env` 只包含：

- `LUNE_PORT=7788`
- `LUNE_DATA_DIR=/app/data`
- `LUNE_CPA_AUTH_DIR=/app/data/cpa-auth`
- `LUNE_GATEWAY_TMP_DIR=/app/data/tmp`
- `LUNE_EMBEDDED_CPA_VERSION=v7.0.2-lune.1`

静态配置没有 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED=1`。这个事实只能说明 Docker 容器配置里没有显式传入该变量，不能证明 Lune 子进程没有拿到 entrypoint 动态 export 的变量。

### 2. PID1 环境复核

在 `lune-0.1.6` 中读取 PID1 环境时，也没有看到 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED`。

这仍然不能作为根因证据。PID1 是 shell entrypoint，它会在 `run_embedded_cpa` 分支中 `export LUNE_CPA_PROVIDER_PINNING_SUPPORTED=1` 后再启动子进程。PID1 视图和子进程视图要分开核对。

### 3. 子进程有效环境复核

进一步遍历 `/proc/[0-9]*/cmdline` 和 `/proc/[0-9]*/environ` 后，运行中的 `lune-0.1.6` 容器里实际结果为：

- `lune up` 子进程带有 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED=1`。
- embedded `CLIProxyAPI` 子进程也带有 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED=1`。
- 两个子进程同时带有 `LUNE_EMBEDDED_CPA=1`、`LUNE_CPA_BASE_URL=http://127.0.0.1:8317` 和默认 CPA API key 环境。

因此，对当前真实 `lune-0.1.6` 容器而言，“Lune 进程没有拿到 pinning 环境变量”这个假设被排除。

### 4. 临时容器实跑复核

使用已发布镜像 `noreply1018/lune:0.1.6` 启动临时容器 `lune-0.1.6-audit`，绑定独立 Docker volume，端口使用 `127.0.0.1:11147`，不复用正在运行的 0.1.5 / 0.1.6 数据目录。

临时容器日志显示：

- 新数据库初始化。
- `CLIProxyAPI Version: v7.0.2-lune.1`。
- `CPA runtime auto-configured base_url=http://127.0.0.1:8317`。
- `/healthz` 返回健康。

临时容器同样需要按子进程环境判断，而不是只看 `docker inspect`。测试完成后已删除临时容器和测试 volume。

## 审计结论

本次审计修正了一个初始误判：

> `docker inspect` 和 PID1 环境没有显示 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED=1`，不等于 `lune up` 进程没有该变量。

对当前真实 `lune-0.1.6` embedded CPA 容器而言，`LUNE_CPA_PROVIDER_PINNING_SUPPORTED=1` 已经在 `lune up` 和 `CLIProxyAPI` 子进程中生效。因此，0.1.6 中账号不可用不能再归因于“embedded CPA 没有默认设置 pinning 环境变量”。

剩余排查方向应回到账号、路由和运行时状态本身：

- 直连账号应检查 `base_url`、API token、模型列表、`accounts.status`、`serving_status` 和最近 request log。
- CPA 账号应检查 `credential_status`、`subscription_status`、`quota_status`、`serving_status`、runtime binding 解析结果和 request log 中的 `runtime_binding_status/reason`。
- 强制路由失败时，应区分 `runtime_auth_binding_unavailable`、`no_healthy_account`、`model_not_on_account`、subscription 非 active、账号状态 error 等具体原因。

## 已观察到

- `docker inspect` 的静态环境没有显示 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED=1`。
- PID1 shell 环境没有显示 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED=1`。
- 运行中的 `lune-0.1.6` 里，`lune up` 子进程和 embedded `CLIProxyAPI` 子进程都实际携带 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED=1`。
- 临时容器 `lune-0.1.6-audit` 启动后，embedded CPA 日志显示 `CPA runtime auto-configured base_url=http://127.0.0.1:8317`，`/healthz` 返回健康。

## 由观察推导出的结论

- 不能把 `docker inspect` 或 PID1 环境当作运行时有效环境。
- 不能再把本次 0.1.6 账号不可用简单归因于 pinning 环境变量缺失。
- 需要继续排查账号状态、路由门槛和 runtime binding 解析结果。

## 改进策略

v0.1.7 的诊断能力需要把“静态容器配置”和“运行时有效状态”明确分层，避免用户和维护者再次被误导。

建议新增或增强一个 runtime diagnostics 面板，展示：

- 镜像版本与 embedded CPA 版本。
- `docker inspect` 能看到的容器静态环境摘要。
- `lune up` 进程的有效配置摘要。
- embedded CPA 子进程是否存在。
- embedded CPA 子进程版本。
- Lune 视角的 `provider_pinning_supported` 有效值。
- system_config 中持久化的 `cpa_provider_pinning_supported` 值。
- 当前 gateway router 使用的 `CpaRuntimeBindingSupported` 值。

展示原则：

- 不展示完整 token、完整 auth file 或完整请求内容。
- 明确标注“容器静态配置”和“运行时有效环境”不是同一层。
- 对 embedded CPA，优先展示 Lune 已加载的有效配置，而不是让用户自行从 PID1 或 `docker inspect` 推断。
- 对外部 CPA，必须明确是否由用户显式声明 pinning 能力；未声明时 fail closed 是预期行为。

## 待实现 / 待验收

以下项目是建议验收项，不是本次审计已经证实的运行态事实：

- `system_config.cpa_provider_pinning_supported` 的持久化值是否与运行时 effective pinning capability 一致。
- gateway router 视角的 `CpaRuntimeBindingSupported` 是否与 embedded CPA 实际能力一致。
- `/readyz` 或管理员诊断 API 是否返回 Lune 视角的 effective provider pinning capability。

## UI 表现

诊断页或系统状态页应给出可读结论，而不是只展示原始字段：

```text
Embedded CPA: running
Provider pinning: enabled
Effective source: lune process env
Container env: not explicitly set
```

如果静态容器环境没设置，但运行时有效配置已经启用，应显示为正常，并附带说明：

```text
容器启动脚本在运行时启用了 provider pinning；docker inspect 中看不到该动态 export 是正常现象。
```

如果运行时有效配置未启用，应显示明确阻断：

```text
Provider pinning 未启用
CPA 账号普通流量会 fail closed，避免账号归因错误。
```

账号详情页的 CPA 诊断区也应避免只给出“不可用”结论，应展示不可用来自哪一层：

- runtime capability。
- runtime binding。
- credential。
- subscription。
- quota。
- serving。
- model list。

## 日志与诊断

启动日志应保留以下安全摘要：

- embedded CPA 是否启用。
- CPA base URL。
- provider pinning effective value。
- running CPA version。
- Lune 持久化到 `system_config` 的 provider pinning value。

建议在 `/readyz` 或管理员诊断 API 中返回同类安全摘要，便于无需进入容器也能判断有效运行态。

日志不得记录：

- `CPA_API_KEY` 完整值。
- `LUNE_CPA_API_KEY` 完整值。
- `LUNE_CPA_MANAGEMENT_KEY` 完整值。
- auth file 内容。
- refresh token / access token。

## 测试与验收

### 单元与集成测试

- `LoadConfig` 或 app 启动逻辑应覆盖 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED=1/true` 的解析。
- embedded CPA 启动路径应覆盖 provider pinning effective value 写入 health checker 与 `system_config`。
- router 装配测试应覆盖 `CpaRuntimeBindingSupported=true` 时 CPA 账号可继续进入 runtime binding 阶段。
- router 装配测试应覆盖 `CpaRuntimeBindingSupported=false` 时 CPA 账号 fail closed，并返回明确 reason。

### 容器验收

必须使用真实发布镜像启动临时容器，使用全新数据目录，不复用或影响正在运行的旧容器，用完必须删除。

容器验收至少覆盖：

- `docker inspect` 静态环境可以不包含 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED`。
- `lune up` 子进程有效环境包含 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED=1`。
- embedded `CLIProxyAPI` 子进程存在，版本为发布固定版本。
- Lune `system_config.cpa_provider_pinning_supported` 为 `1`。
- gateway router 视角的 `CpaRuntimeBindingSupported` 为 true。
- 创建 fake CPA 账号后，强制路由不会因 `provider_pinning_unsupported` 被提前拒绝；若缺少 auth metadata，应失败在 runtime binding 缺失，而不是 capability 缺失。

如果容器缺少 shell 工具，测试脚本应使用 `/proc` 读取进程信息，不依赖 `ps`、`jq` 或 `sqlite3` 必然存在。

## 已完成事项

- 已只读审计运行中的 `lune-0.1.5` 与 `lune-0.1.6` 容器。
- 已确认 `lune-0.1.6` 的 `docker inspect` 静态环境不包含 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED`。
- 已确认运行中的 `lune-0.1.6` 里，`lune up` 子进程和 embedded `CLIProxyAPI` 子进程都实际携带 `LUNE_CPA_PROVIDER_PINNING_SUPPORTED=1`。
- 已使用 `noreply1018/lune:0.1.6` 启动临时容器完成 embedded CPA 启动复核。
- 临时测试容器 `lune-0.1.6-audit` 和测试 volume `lune-0.1.6-audit-data` 已删除。

## 待解决事项

- 继续排查 0.1.6 中直连账号和 CPA 账号不可用的真实阻断层，不能再把根因默认归到 pinning 环境变量缺失。
- 增加系统诊断 API 或诊断页，直接展示 Lune 视角的 effective provider pinning capability。
- 在容器验收中补齐“静态 env 缺省但子进程 effective env 正确”的专项断言。
- 在故障页面中区分 `provider_pinning_unsupported`、runtime binding 缺失、subscription 非 active、账号 status error、model list 拒绝等路由阻断原因。
